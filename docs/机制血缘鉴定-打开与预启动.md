# 🔬 机制血缘鉴定 —— “打开指定 App” 与 “预启动” 的来龙去脉

> 定稿：2026-09-20 22:15 ｜ 作者：Operit AI
> 方法：各版本 jar 字符串扫描 + smali 坐标核验 + 客户端解码树（/tmp/c9dec、/tmp/c12、/tmp/c13dec）
> 一句话结论：**“打开 App”是原版自带能力（PackageManager + AMS 直投）；“预启动”（auto-prewarm）是 v5 才加入的我方补丁功能；两者共用同一个 launchApp，不存在两套打开机制。冲突风险只来自“目标不一致”，已由 v4（任务感知）结构性消除。**

## 一、原版是怎么打开 App 的（全链路证据）

```
任务链步骤 {"action":"Launch","app":"腾讯视频"}
  → [客户端] ActionHandler.executeAgentAction
  → ShowerController.launchApp(agentId, packageName)      // agentId 默认 "default"
  → [showerclient] ShowerController$launchApp$2 协程：取本会话 virtualDisplayId
  → IShowerService$Stub$Proxy.launchApp(pkg, displayId)   // Binder 事务号 0x3
  → [服务器] IShowerService$Stub :pswitch_a 分支
  → u2/g.launchApp(pkg, displayId)：
      ① PM.getLaunchIntentForPackage(pkg)                 // 拿启动 Intent
      ② addFlags(FLAG_ACTIVITY_NEW_TASK)
      ③ ActivityOptions.setLaunchDisplayId(displayId)     // 经 c1/k0 桥接
      ④ 反射 ActivityManagerNative.getDefault()
         → startActivityAsUser(..., "com.android.shell", ..., options, userId=-2)
  → 系统把该 App 的 Launcher Activity 直接启动到虚拟屏 displayId 上
```

关键坐标：
- g.smali:1576 `launchApp(Ljava/lang/String;I)V`（含日志 “launchPackageOnVirtualDisplay: started / no launch intent for / invalid displayId”）
- g.smali:2747-2790 Binder stub `:pswitch_a`（readString + readInt → launchApp → writeNoException）
- IShowerService.smali:25（抽象方法）；Stub:39（TRANSACTION_launchApp=0x3）；Proxy:425
- 客户端：c12 `ActionHandler.smali:7054 / 7451`；c12 `ShowerController.smali:785 / 812`；c13 `ShowerController$launchApp$2.smali:272`
- 运行时印证：21:52:17.406 `launchPackageOnVirtualDisplay: com.tencent.qqlive on 59`（任务链第 1 步 Launch）

**结论：全程无 UI 寻址、无坐标、无“遍历找图标”——是毫秒级 Intent 直投。这就是原版的“快捷打开机制”。**

- 预启动实现：g.smali:6078 `schedulePrewarm`（建屏成功后被调用，见 g.smali:1320 `:prewarm_skip` 人工标签）→ new Thread(u2/x) → x.smali:run()：sleep 2.5s → 读 /data/local/tmp/prewarm_target.txt（需 exists 且 mtime 距今 ≥ 300000ms=“5 分钟冷却”）→ 调 g.launchApp(target, displayId)。
- “5 分钟冷却”为原设计防抖（只认沉淀 ≥5min 的稳定配置；推断意图：防误触发/防调试中半成品配置生效）。
- v4 脚本以 `touch -t 202601010000.00` 冻龄绕过，使“任务感知动态配置”即时生效。
- 提速数字对账：v5 预启动 = 建屏后 2.5s + 拉起 ≈ 2.53s（任务 A 验收值）；无预启动基线 = 任务链走到 Launch ≈ 8.86s（v4 基线）。

## 三、为什么说“不冲突”（设计层面）

1. **同一只手**：预启动最终调用的是同一个 `u2/g.launchApp`（x.smali:74），与任务链走的是同一条 Binder/AMS 通道——不是两套机制。
2. **不是同时**：预启动在建屏后 ~2.5s；任务链 Launch 在 ~8.9s。先后两次“按同一个按钮”。
3. **目标一致时无害**：两次拉起同一 App = 第二次相当于带到前台/no-op；这正是 v5.4 复测通过的提速场景。
4. **真正的风险 = 目标不一致**：预启动拉 A（抖音）、任务链拉 B（腾讯）→ 同一虚拟屏先后进驻两个 App → 输出/焦点竞争 → 画面异常（透明空白）+ WS 截图 no data（21:42 案例）。
5. **v4 结构性消除**：预启动目标永远 = 任务目标（prewarm_map.tsv 解析）；识别不出 → 写空文件 → 预启动自动跳过（宁缺毋滥）。要么同目标，要么零预启动。

## 四、否证：“复制主屏、一点点找应用” ×

- 打开动作 = PM + Intent + AMS 直投（无 UI 寻址）。
- 虚拟屏 ≠ 主屏复制：它是 MediaCodec 输入 Surface 为画布的独立空屏（DisplayManager.createVirtualDisplay），App 由 AMS 布置其中；主屏（display 0）与它互不干扰。
- “一点点找/点”的是任务链后续 UI 步骤（App 已打开之后），且由模型看截图决策，不是遍历图标。

## 五、对 v4 的意义与已知限制

- v4 保证：a) 目标一致性；b) 无法识别时不预启动；c) 同目标重复启动无害；d) 通道与权限沿用服务器内置（成功率高）。
- 建议持续动作：prewarm_map.tsv 按新 App 持续扩充；观测点 = prewarm.log 出现 `read → calling → launched on display N` 即为预启动干活。
- 不变约束：同一 App 不能同时开两个虚拟屏任务（官方产品约束）。
