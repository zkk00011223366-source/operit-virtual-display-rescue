## 1. 问题档案（这一切为了解决什么）
### 1.1 虚拟屏“空白”故障（核心问题）
- 症状：虚拟屏有声音没画面 / 悬浮球空白 / AI 识别主屏并按其操作（点击无效）
- 根因（已实锤）：预启动提前拉起 app → 约 3 秒 ≈120 帧把客户端环形缓冲（上限 120）撑满 → 丢头把含 SPS/PPS（csd）的帧挤掉 → 解码器永不初始化 → 整场空白
- 两类空白：竞态型（有画面但解码断） vs 未拉起型（根本没打开 app，如任务名错误）
- 判定指纹：`replaying 120 buffered frames`（竞态）；`[xxx] Shower WS screenshot returned no data`（AI 侧信号）；空屏截图 = 18870 字节
- 详见：《案例记录-竞态空白实锤-replaying120.md》
### 1.2 任务慢 / 打开 app 慢
- 打开机制本身毫秒级（Launch 直拉，实测 29ms）
- 慢在“AI 磨蹭”（实测 13~71 秒后才执行打开动作）
- 预启动（本方案）把“打开就绪”提前到建屏后 ~2.5 秒；v6 修复后兑现速度红利
### 1.3 安卓 17 / MagicOS 环境事项
- MagicOS 后台冻结机制：常驻脚本需白名单放行；Shizuku 需保持运行
- 虚拟屏依赖 app_process（Shizuku-style binder handoff）；系统更新后可能需要重新授权
- （详细兼容点清单待 v1.0 汇总）

## 6. v6 修复（已验收 · 2026-09-21）
### 6.1 根因回顾
- 预启动提前拉起 app → 约 3 秒 ≈120 帧把客户端环形缓冲（上限 120）撑满 → 含 SPS/PPS（csd）的头部帧被挤掉 → 解码器永不初始化 → 整场空白（详见《案例记录-竞态空白实锤-replaying120.md》）
- 另：Android 17（SDK 37）删除了 `InputManager.getInstance()`，原触控注入初始化抛 NoSuchMethodException → 所有注入失效（"能显示但点击无效"）
### 6.2 设计
- 空白竞态：服务器侧对 SPS/PPS/IDR 关键帧做缓存 + 每 60 帧周期性重发；异常不再静默（加日志）
- 触控：改走新 API 链 —— `InputManagerGlobal.getInstance().mIm.injectInputEventToTarget(event, mode, displayId)`（u2/f 字节码重建）
### 6.3 部署与回滚
- 产物：shower-server-v6.jar（md5 43fd817e4f35b7914a0b7e92effa1642）
- 副本：v6 源 + shower-server.jar（DL）+ /data/local/tmp + backup_20260920/（4 副本一致；watchdog SRC=v6 自动对齐）
- 回滚：`sh /sdcard/Download/Operit/rollback_to_v5.sh`（或按 PATCH_PROGRESS.md 原版覆盖法）
### 6.4 验收记录（2026-09-21 00:02~00:15）

### 6.5 v9 —— 空白自愈「真·修复」（已验收 · 2026-09-21 07:28）
- **重大发现**：v6~v8 的 NAL 扫描器实为坏件（条件分支错位 + 提前退出逻辑写反）——v6 时代那条 `cached SPS frame` 是分流错位歪打正着的表象，PPS 从未存上、周期重发从未真正生效
- **修复**：重写扫描器 `v9NalMask`（严格 `00 00 01` 起始码；SPS/PPS/IDR 掩码 0x80/0x100/0x20；集齐 0x1a0 提前返回）+ 缓存守卫 3 处 + 重发判定 2 处
- **验证三重奏**：①独立小程序字节级实验（5 组样本全对：128/128/32/416/416）；②产物反编译复核（守卫/重发/日志齐备）；③实机单会话（display81）全链路日志：`v9: cached SPS` → `cached PPS` → `cached IDR` → 4× `periodic resend done`，画面渲染正常、测后无残留
- **产物**：shower-server-v9.jar（md5 `038be08b890c430b9e032642898a84e9`，size 1163819）；构建套件 `v9_build_kit.tar.gz`
- **部署/回滚**：`deploy_v9.sh`（已执行）｜ `rollback_to_v8.sh`（v9→v8）｜ `restore_chain_v5.sh`（v9 基线一键恢复）
- **教训**：日志标记 ≠ 机制生效；判定必须「独立实验 + 实机全链路」

### 6.6 v9.1 —— 周期性黑闪修复（窗口化重发 · 已验收 · 2026-09-21 08:40）
- **问题**：v9 上线后用户实测发现虚拟屏“约 1.5 秒一黑闪”（整屏像一开一关）；取证实锤：闪的节奏与 v9「每 60 帧永久重发」完全吻合 → 重发帧在客户端引发周期性解码链重置
- **方案（不偏极端）**：窗口化重发 —— 前 6 次（60~360 帧）保留防空屏保护，360 帧后彻底静默
- **改动仅两处**（相对 v9）：重发判定块 `rem-int` 取模 + `0x168` 上限；日志串改版 `v9.1:`
- **构建**：make/patch/make_jar 三脚本程序化改写 + 四层复核（构建链 / dex 指纹同源 / 字符串指纹 / 环回反编译）全绿
- **验证（实机两场景）**：
  - 美团（静态 ~4fps）：6 次重发拉长到约 1 分钟，随后静默（≥5 分钟无新增，期间 28 步密集操作）
  - 腾讯视频（播放满帧 60fps）：6 次压缩到 5.16 秒跑完，随后静默；画面流畅
  - 用户确认：“现在不闪了” ✅
- **产物**：shower-server-v9.1.jar（md5 `e8c1b771e34aa523cde83af3139aa41a`，size 1163846）；构建套件 `v9_1_build_kit.tar.gz`
- **部署/回滚**：`deploy_v9_1.sh`（已执行；含 hc/恢复链升版）｜ `rollback_to_v9.sh`（v9.1→v9）｜ `restore_chain_v6.sh`（v9.1 基线一键恢复）
