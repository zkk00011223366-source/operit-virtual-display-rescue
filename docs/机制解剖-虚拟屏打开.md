# 🔬 机制解剖 · 虚拟屏是怎么被"打开"的（定稿 v1）

> 定稿：2026-09-20 19:25 ｜ 作者：Operit AI ｜ 配套：《项目记录-虚拟屏技术链.md》《系统保护清单-勿删勿拆.md》
> 范围：从"用户点执行任务"→ 服务器进程启动 → Binder 交接 → 建屏 → 小窗显示 → 关闭/自愈 的**全链路**。
> 证据来源：classes9/12/13.dex 与 shower-server.jar 全解码（研究现场：/tmp/c9dec、/tmp/c12/dec、/tmp/c13dec、/tmp/ssx_dec）+ 运行时日志（shower.log / prewarm.log / logcat_mon.log）。

---

## 0. 一句话总览

```
[用户点"执行任务"]
 → AutoGlmViewModel（决定 useVirtualScreen）
 → PhoneAgent.ensureRequiredVirtualScreenOrError（查重 → 权限闸门 → 拉服务器 → 建屏 → 显示小窗）
 → ShowerServerManager.ensureServerStarted（shell 拉起独立服务器进程：app_process 跑 shower-server.jar）
 → 服务器通过【广播】把 Binder 递给 App（Shizuku 式交接，不走 ServiceManager.addService）
 → App 调 IShowerService.ensureDisplay(w,h,dpi,bitrate)
 → 服务器用 MediaCodec 输入 Surface 建 DisplayManager 虚拟屏 → 返回 displayId
 → App 小窗（VirtualDisplayOverlay）显示画面；服务器无客户端 15s 自退。
```

## 1. 触发点（谁在"打开"）

- **UI/任务层**：`AutoGlmViewModel.executeTask`（classes9.dex → `.../ui/features/toolbox/screens/autoglm/AutoGlmViewModel$executeTask$1.smali`）
  四条用户可见日志（对应四个环节，均出自此文件）：

  | 日志 | 环节 |
  |---|---|
  | `[VirtualScreen] Ensuring Shower virtual display...` | 开始确保虚拟屏 |
  | `[VirtualScreen] Failed to start Shower server.` | 服务器拉起失败 |
  | `[VirtualScreen] Failed to create virtual display for agentId=` | 建屏失败 |
  | `[VirtualScreen] Virtual display ready. displayId=` | 建屏成功（拿到 displayId） |

- **Agent 层**：`PhoneAgent.ensureRequiredVirtualScreenOrError`（classes12 → PhoneAgent.smali **:1825-2328**；调用点 **:8155**，在 PhoneAgent.run 流程里）

## 2. 客户端主链（"确保虚拟屏"7 步·按 smali 解码顺序）

1. `hasShowerDisplay()` —— **查重**：已有可用虚拟屏 → 直接复用（不重复建）
2. `resolvePrivilegedExecutionState()` —— 解析特权执行状态（Shizuku/root 可用性）
3. **闸门检查**：`isAdbOrHigher` + `hasDebuggerShizukuAccess`（对应 GUI"权限级别 DEBUGGER/ADB"）
4. `ShowerServerManager.ensureServerStarted(context)` —— 保证服务器进程 + Binder 就绪（见 §3/§4）
5. 取屏幕参数：宽高/Dpi + 偏好码率（实测：`1264x2608 dpi=560 bitRate=4000000`）
6. `ShowerController.ensureDisplay(agentId, ctx, w, h, dpi, bitrate)` → `getDisplayId()`（suspend，返回 Boolean；内部走 Binder，失败自动重试一次）
7. `VirtualDisplayOverlay.show()` —— App 侧小窗显示（画面来自服务器视频流）

（失败路径对应日志："Failed to start Shower server" / "Failed to create virtual display"）

## 3. 服务器启动（ShowerServerManager.ensureServerStarted · showerclient 库）

- **前提**：`ShowerEnvironment.shellRunner` 已由 App 注入（实现类 `OperitShowerShellRunner` → `AndroidShellExecutor`，即 Shizuku/Root 通道）。
  身份映射：`ShellIdentity` DEFAULT/SHELL/ROOT → App 侧同名枚举。
- **快路径**：`ShowerBinderRegistry.hasAliveService()` 已有存活 Binder → **跳过启动**（日志 "Shower Binder already cached and alive, skipping start"）。
- **慢路径**（依次执行，全部经 ShellRunner）：

  | # | 命令（原文） | 身份 | 作用 |
  |---|---|---|---|
  | 1 | `pkill -f com.ai.assistance.shower.Main \|\| true` | DEFAULT | 杀旧服务器 |
  | 2 | `rm -f /data/local/tmp/shower-server.jar /data/local/tmp/shower.log \|\| true` | DEFAULT | 清旧 jar/日志 |
  | 3 | `cp <jar> /data/local/tmp/shower-server.jar` | SHELL | 部署 jar |
  | 4 | `CLASSPATH=/data/local/tmp/shower-server.jar app_process / com.ai.assistance.shower.Main <包名> &` | SHELL | **拉起服务器** |

- **jar 来源**：App assets 里的 `shower-server.jar` 先复制到 `/sdcard/Download/Operit/shower-server.jar`（copyJarToExternalDir），再 cp 到 `/data/local/tmp`。目标包参数默认为 App 自己（`getPackageName()`，逗号分隔可含 additionalTargetPackages）。
- 启动后**轮询等待 Binder**（日志 "Shower Binder cached and alive after ~Nms"；超时报 "not received within the expected time"）。
- ⚠️ **关键竞态**：第 3 步会用自己的 jar **覆盖两处副本**——若 App assets 是原版，补丁就被清掉；这正是**看门狗存在的意义**（0.05s 抢修；18:30 内存验尸实锤服务器加载的是 v4）。

## 4. Binder 交接（Shizuku 式 · 不做 ServiceManager.addService）

**服务器侧（Main.g）**：
- 构造 `Intent("com.ai.assistance.operit.action.SHOWER_BINDER_READY")` + `FLAG(0x20 = INCLUDE_STOPPED_PACKAGES)` + extra **`binder_container`** = `ShowerBinderContainer(serverBinder)`
  （Parcelable，内部 `writeStrongBinder` —— 即所谓 "Skip ServiceManager.addService by design"）
- 目标包来自 `Main.f`（启动参数 args[0]，逗号分隔）→ 逐个 `setPackage(...)` 发送（反射 IActivityManager 通道）

**App 侧（ShowerBinderReceiver）**：
- `onReceive` → 读 `binder_container` → `getBinder()` → `IShowerService$Stub.asInterface` → 检查 `isBinderAlive` → `ShowerBinderRegistry.setService()`（静态缓存）

**获取/自愈（ShowerController$Companion.getBinder）**：
- 尝试循环：取缓存 Binder 并检查存活；失败若干次后 → 调 `ShowerServerManager.ensureServerStarted` **重启服务器**再取（"attempting to restart Shower server after connection failure"）
- 死 Binder 会先清理（clearDeadService，同时清 Controller 缓存与 Registry）

## 5. 建屏（服务器 u2/g.ensureDisplay(IIII)I —— /tmp/ssx_dec）

**输入**：宽、高、dpi、码率（App 传 4 Mbps；尺寸 16 对齐由客户端 `alignToCodecBlockSize` + 服务器 "aligned size" 双重保障）

**流程（u2/g）**：
1. 日志：`ensureVirtualDisplay requested: WxH dpi=… bitRate=…`
2. `MediaCodec.createEncoderByType("video/avc")` → 配置（bitrate / frame-rate=30 / i-frame-interval=1）→ `createInputSurface()`（**编码器输入 Surface = 虚拟屏画布**）→ `start()`
3. `DisplayManager.createVirtualDisplay("ShowerVirtualDisplay-<ms%1000>", w, h, dpi, surface, flags)` → 得 displayId
   （**系统级递增**：33/34/35/36…；名字里的数字不是系统 id）
4. 注册会话 `DisplaySession(id, VirtualDisplay, MediaCodec, Surface, InputController, videoSink)`（类 u2/j）
5. `WindowManager.setDisplayImePolicy(LOCAL, id)`；`InputController` 初始化并把注入目标切到该 id（日志 "InputController.setDisplayId: N"）
6. 返回 displayId 给 App

**交互/画面/截图**：
- 触摸/按键：App → `IShowerService.tap/swipe/injectTouchEvent/key...` → 服务器注入到对应 display（v3 补丁修正荣耀 ROM 参数顺序）
- 画面：App `setVideoSink(id, IShowerVideoSink)` 注册接收端；服务器编码帧回传；App `ShowerVideoRenderer.attach(surface,w,h)` 渲染小窗
- 截图（眼睛）：服务器 `requestScreenshot(id)` 走 **SurfaceControl API + ImageReader**（v4 补丁：主屏请求重定向到活跃虚拟屏）；**shell screencap 抓不了虚拟屏**（实测 "Display Id 'N' is not valid"）。

## 6. 关闭与自愈

- 屏释放：`Releasing display session N` → `InputController.setDisplayId: 0`
- 服务器闲时自退：无 Binder 客户端 **15000ms** → "No active Binder clients for 15000ms, exiting"（b/g 看门机制；约 1s 粒度轮询）
- 下次任务：快路径命中不了 → 自动重新拉起（自愈）→ 看门狗保障补丁版
- 实测时间线：19:08:41 释放 36 屏 → 19:08:57 服务器自退（15s 后）；18:30 场次亦由 App 自动拉起（非手工）

## 7. 与我们的改造 / 哨兵的关系

- **v3（注入参数修正）**：作用点在服务器 u2/f InputController —— 让"点得有效"（一号验收线）
- **v4（截图纠偏）**：作用点在服务器截图路径 —— "眼睛"
- **看门狗**：对抗 §3 竞态；双副本（DL+TMP）尺寸校验 + v4 源修复
- **抢跑哨兵 v3 复盘**：18:59:50 建屏 36 → 哨兵 4s 后起、6 次×2s（~15s 窗口）全 `Failed transaction`；而 19:08 手打 `am start --display 36` 两次全 rc=0 → **"门未就绪"**：建屏后系统/会话还需要更长准备期才可接受 `am start`。改进方向：窗口延长至 ≥60s（或探测到"就绪信号"再打门），持续轮询。
- **logcat 取证网**：监听关键字（Shower / VirtualDisplay / PhoneAgent…）
- **重装注意**：卸载重装后首次运行，App assets 原版 jar 会覆盖两副本 → 看门狗毫秒级抢修；若观察首跑异常，先跑 `restore_chain.sh` 复核。
