**用户视角**：在 Operit 发一个任务（例："打开腾讯视频播放仙逆"），勾选"虚拟屏" →
1. "舞台"即刻就绪（秒级，最好不用等）
2. 目标 APP 自动就位，AI 直接开干
3. AI **看得见、点得准、点得有效**——点完虚拟屏界面**真的有反应**（按钮真按下、界面真变化、操作真生效），不瞎点、不空点、不干等
4. 可随时预览（小窗）；任务完成后 APP 可留在虚拟屏后台（如腾讯视频那样）
5. 稳定不卡死，长任务（25步）能跑完

## 二、我们从哪里开始（起点：2026-09-20 上午）

- **症状（项目开端）**：**在虚拟屏里点击/滑动后界面毫无反应**——“点了没反应”的假屏：按钮不按下、界面不变化、操作全部无效（用户最初判断“安卓17不兼容”，正确！）
- **这就是本项目的开端**：核心验收线 =「**点完虚拟屏界面要有效**」（不只是点得准）——后续所有优化都服务这条线。
- **双根因（dexdump 实锤）**：
  1. `InputManager.getInstance` 被 Android 17 **删除** → 注入调用直接失效
  2. 荣耀 ROM 上 `IInputManager$Default.injectInputEventToTarget(event, displayId)` **参数顺序与 AOSP 相反**（实际要求 `(displayId, event)`）→ 注入错屏/无效
- **第一步修复**：v3 补丁（参数修正）+ 看门狗（防 Operit 每次会话用原版覆盖）

## 六、重装/更新 Operit 后的快速恢复 ⭐（用户重点关心）

**先说结论**：技术链大部分活在 APP 之外（`/data/local/tmp` + `/sdcard`），**卸载重装不受影响**；真正要重做的只有 3 项 GUI 设置 +（换新版本时）补丁兼容性检查。

### 6.1 自动恢复（一键）
```sh
sh /sdcard/Download/Operit/restore_chain.sh
```
它会自动：检查/补齐 v4 三副本 → 恢复缺失脚本 → 启动缺岗的看门狗/哨兵/logcat → 输出自检报告（`restore_chain.log`）

3. **实验性虚拟屏开关**：打开
（建议顺带：给 Operit 开无障碍服务）

## 八、虚拟屏打开机制（2026-09-20 定稿 · 摘要）

> 完整版（代码坐标/证据/复盘）：**《机制解剖-虚拟屏打开.md》**

**六步一句话**：①点“执行任务”→`AutoGlmViewModel`→`PhoneAgent.ensureRequiredVirtualScreenOrError` ②权限闸门+查重 ③`ShowerServerManager` 用 shell 拉起服务器（`.../shower-server.jar` + `app_process ... Main <包名> &`）④服务器**广播**把 Binder 递给 App（Shizuku式）⑤App 调 `ensureDisplay` → 服务器用 **MediaCodec 输入 Surface** 建 `DisplayManager` 虚拟屏 → 返回 displayId ⑥小窗显示；无客户端 15s 自退、下次自动重启。

**对本链意义**：App 每次启动都会用原版 jar 覆盖两处副本 → **看门狗=补丁保真关键**（18:30 内存验尸实锤 v4）；哨兵失败=门未就绪，需延窗。

**任务**：AI 用 UI 子代理执行“打开抖音刷五条视频”（com.ss.android.ugc.aweme），两种模式各一次：`run_subagent_virtual`（agent_id=dy_test_1）/ `run_subagent_main`（agent_id=default）。

### 机制级新发现（重要）
1. **主屏模式同样走 Shower 服务器**：不建屏、同款 DisplayCapture 截图 + Binder 注入，仅 displayId=0。两模式共用同一技术栈，差异只在“有没有虚拟显示屏”。
2. **启动通道差异**：虚拟屏=launchPackageOnVirtualDisplay API；主屏=先 `Binder KEY injected` 再 shell(uid2000) START。
3. **看门狗第 5/6 次救场**：19:45:51（DL）、19:49:01（DL+TMP）——每次任务启动都会把 jar 重置为原版 1133303B，看门狗全部修回 v4（1162878B）。补丁保真=看门狗在干活。
4. **哨兵第 5 次全败（display 40），根因修正**：非“窗口太短”——建屏后 4s 连打 6 次（跨 10s）仍全 Failed transaction；同期服务器同 uid 的 Binder 通道一次成功。修法=哨兵改用服务器同款 Binder API。
5. 两次实际滑动均 4 次（子代理自述“5 次”为表达误差），均覆盖 5 条视频；**“操作真实有效”双通过（一号验收线）+ 截图路由生效**。

### PhoneAgent 执行链（源码级坐标 · 2026-09-20 补录）
- **入口**：`StandardUITools.runUiSubAgent(StandardUITools.kt:461)` → `PhoneAgent.run(PhoneAgent.kt:355/371/376)`
- **两条互斥准备分支**：
  - 虚拟屏模式 → `PhoneAgent.kt:371` → `ensureRequiredVirtualScreenOrError(PhoneAgent.kt:216)`：确保虚拟屏（binder 死→自动重启服务器→建屏）
  - 主屏模式 → `PhoneAgent.kt:376` → `prewarmMainScreenShowerIfPossible(PhoneAgent.kt:305)` → `ShowerController.prepareMainDisplay(ShowerController.kt:165)`：**主屏预热 + 预启动目标 app**（19:49:02.494 日志实锤：`run: prewarming main-screen launch via Launch(app='com.ss.android.ugc.aweme')`，早于 step1 @19:49:03.558）
- **子代理循环**：每步 `_executeStep` = 截图（`ActionHandler.captureScreenshotViaShower`，失败自动重试）→ 模型推理 → 动作注入（Binder SWIPE / launch）
- **实测对照**：
  - 虚拟屏 7 步 = 1×Launch（模型触发，把 app 拉进屏）+ 1×Wait + 4×Swipe + 1×完成；首次进屏 8.8s（含模型第 1 轮推理）
  - 主屏 5 步 = 预启动（框架）+ 4×Swipe；调用→进屏 1.5s
- **产品细节**：主屏模式自动加“rainbow border overlay”（彩虹边框）提示 AI 正在操作；虚拟屏无需（独立小窗 ShowerSurfaceView）
