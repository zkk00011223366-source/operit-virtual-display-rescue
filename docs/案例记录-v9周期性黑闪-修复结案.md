# 案例记录 · v9 周期性黑闪（修复结案）

> 现象：用户实测“约 1~2 秒一黑闪，整屏像一开一关” ｜ 状态：**已修复（v9.1）** ｜ 时间：2026-09-21
> 关联：《手册 v1.2》§6.6 ｜《PATCH_PROGRESS.md》v9.1 条目 ｜《性能记录-打开耗时.md》v9.1 节奏验证

## 一、现象与观察（用户实测）
- 发现场景：美团下单任务会话中（2026-09-21 08:0x），用户发现虚拟屏“一闪一闪”
- 用户描述：“差不多一两秒闪一下，一黑一黑的，整个虚拟屏的显示就像一开一关那样”
- 初始猜测：帧率问题？（实际不是）

## 二、定位过程（08:08~08:12）
1. **节奏取证**：`shower.log` 里 `v9: periodic resend done` 稳定以 **≈1.53 秒** 间隔出现（08:08:11→28 共 12 次，间隔 1.5~1.7s）
2. **节奏比对**：与用户描述“1~2 秒一下”**完全吻合** → 锁定 v9“每 60 帧永久重发”机制
3. 客户端侧参考取证：解码器 TraceLog（Queued≈Done≈43fps、Discarded 0）；编码器 TraceLog Discarded≈Done 异常模式（待判，与本案例无关）

## 三、根因
- v9 为防“空白”引入「每 60 帧重发一次 SPS/PPS/IDR」的保护，**永久循环**
- 重发帧进入客户端解码链时引发**周期性解码链重置** → 整屏“一开一关”式黑闪
- 性质：**v9 的副作用缺陷**（修好了空白，引入了周期性闪烁）；不是客户端故障、不是帧率不足

## 四、修复方案（v9.1 窗口化重发）
- 原则（用户原话）：“如果是你设置的原因，你可以优化一下，不要太高，太高容易空屏，太低容易一闪一闪” → **不偏极端：保防空屏 + 消闪**
- 方案：仅改两处（相对 v9）：
  1. 重发判定块：`rem-int v3, v0, 0x3c; if-nez v3, :done; const/16 v3, 0x168; if-gt v0, v3, :done` —— 60 的倍数才重发，且 v6Cnt>360 后彻底静默
  2. 日志串：`v9: periodic resend done` → `v9.1: periodic resend done`（失败态同步：`v9.1: resend failed (ignored)`）
- 行为：前 6 次（60/120/180/240/300/360 帧）保留防空屏保护 → 之后**永久静默**

## 五、构建与复核（全绿）
- 程序化构建（make / patch / make_jar 三脚本）+ 四层复核：构建链 ✓ / dex 指纹同源 ✓（apk dex ≡ jar dex，且与 v9 确为不同版本）/ 字符串指纹 ✓ / 环回反编译 ✓
- 产物：shower-server-v9.1.jar（md5 `e8c1b771e34aa523cde83af3139aa41a`，size 1163846）

## 六、实机验证（双场景 + 强静默证据）
| 场景 | 帧率 | 6 次重发 | 之后静默 |
|---|---|---|---|
| 美团（静态页） | ~4fps | ≈61 秒（12~15s/次） | ≥5 分钟无新增（期间 28 步密集操作） |
| 腾讯视频（播放） | 满帧 60fps | **5.16 秒**（≈1.0s/次） | ≥1 分钟无新增 |

- 用户最终确认：**“现在不闪了”** ✅

## 七、结案
- v9.1 已部署（`deploy_v9_1.sh`）并实机验证；回滚位 `rollback_to_v9.sh`、恢复 `restore_chain_v6.sh`
- 教训沉淀：
  1. **周期性 UI 异常 → 先量节奏、再比机制**（节奏匹配是本案例定位的关键手段）
  2. **修复要留保护窗口**（不偏极端原则）：保护不等于永久重复
  3. 判定补丁生效：看“计数封顶”证据（≤6 条 + 静默），而非只看单条日志
